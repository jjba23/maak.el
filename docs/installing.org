* Installing maak.el

Four routes to the same release, from the most automated to the most manual, and
they all build the tag the [[file:../NEWS.org][release notes]] document.  Everything else in this
guide assumes one of them put ~maak.el~ on your ~load-path~.

** Requirements
:PROPERTIES:
:CUSTOM_ID: requirements
:END:

GNU Emacs 28.1 or newer, which is what ~Package-Requires~ says and what the
suite runs on, and [[https://github.com/jjba23/maak][maak]] itself, since
~maak.el~ runs tasks by calling it.  The package reads your Maak file itself, so
it needs no Guile of its own; when the maak helper is not on your ~PATH~, point
~maak-executable~ at it (see [[file:customization.org][Customization]]).

~maak.el~ is not (yet) in MELPA or ELPA, so the four routes below are how it
arrives.

** From the Guix channel
:PROPERTIES:
:CUSTOM_ID: from-the-guix-channel
:END:

*GNU Guix* is the functional package manager this project is developed with: a
build is a pure function of its inputs, so the same recipe gives the same result
everywhere, and an upgrade that goes wrong can be rolled back.

The jointhefreeworld channel carries ~emacs-maak~, so a checkout of the channel is
enough — no package definition to write:

#+begin_src shell
git clone https://github.com/jjba23/guix-jointhefreeworld.git
guix install -L ./guix-jointhefreeworld emacs-maak
#+end_src

Add the channel to ~$HOME/.config/guix/channels.scm~ (the channel's README has
the four lines) and a plain ~guix install emacs-maak~ keeps working on every
later ~guix pull~.  The channel pins its own revision, so what it carries is
whatever its last update said; ~guix show emacs-maak~ is the answer.

** From the Nix flake
:PROPERTIES:
:CUSTOM_ID: from-the-nix-flake
:END:

*Nix* offers the same declarative, reproducible model with its own language, its
own store and a binary cache, and it is a natural fit if the rest of your machine
is already described in Nix.

The jointhefreeworld flake builds this project with this repository's own
expression, so the package cannot drift from the source:

#+begin_src shell
nix build github:jjba23/nix-jointhefreeworld#emacs-maak
#+end_src

The same attribute is available as an overlay, so
~pkgs.jointhefreeworld.emacs-maak~ works inside a NixOS or home-manager
configuration too.  This repository's own ~default.nix~ builds the checkout, so
~nix-build~ here builds what you are reading.

** As a container image
:PROPERTIES:
:CUSTOM_ID: as-a-container-image
:END:

*Podman or Docker* is the route that puts nothing on the host: the ~Dockerfile~
in this repository builds the project in a builder stage and copies only what it
installed into a runtime stage, so the image is small and the host keeps its own
toolchain untouched.

#+begin_src shell
podman build -t maak-el .   # docker build -t maak-el . also works
podman run --rm -it maak-el
#+end_src

The image's entry point is Emacs, with ~maak.el~ installed and byte-compiled,
which makes it useful for a quick try and for reproducing a bug on a clean
system.

** As a distribution package
:PROPERTIES:
:CUSTOM_ID: as-a-distribution-package
:END:

*Debian, openSUSE and Arch* each get the project through their own package
manager.  Packaging lives in this repository under ~packaging/~ and is pinned to
the same release tag, so the recipes and the sources they build are versioned
together.

None of the three archives ships ~maak.el~ yet, so these are recipes to build
rather than packages to install from a mirror:

| Distribution   | Package      | How to build it                                                                     |
|----------------+--------------+-------------------------------------------------------------------------------------|
| Debian, Ubuntu | ~elpa-maak~  | copy ~packaging/debian~ to the repository root, then ~dpkg-buildpackage -us -uc -b~ |
| openSUSE       | ~emacs-maak~ | ~osc build~ with ~packaging/opensuse~                                               |
| Arch           | ~emacs-maak~ | ~makepkg -si~ in ~packaging/arch~                                                   |

Each recipe carries its own dependency list, so a missing library fails the
build with its name rather than producing a package that cannot load.

** With Elpaca
:PROPERTIES:
:CUSTOM_ID: with-elpaca
:END:

Elpaca builds from the repository itself:

#+begin_src emacs-lisp
(use-package maak
  :ensure (:host github :repo "jjba23/maak.el" :branch "trunk")
  :demand t
  :bind ("C-c m r" . maak-run-task))
#+end_src

** From a checkout
:PROPERTIES:
:CUSTOM_ID: from-a-checkout
:END:

Two lines of Emacs Lisp, if the repository is already on disk:

#+begin_src emacs-lisp
(add-to-list 'load-path "/path/to/maak.el")
(require 'maak)
#+end_src

Or, from a checkout you keep installed with Nix,
~emacsPackages.overrideScope~ takes the overlay ~nix-jointhefreeworld~ exports,
so an Emacs that Nix builds gets it the way it gets any other package,
byte-compiled and with its autoloads:

#+begin_src nix
let
  emacsPackages = pkgs.emacsPackages.overrideScope nix-jointhefreeworld.emacsOverlay;
in
  emacsPackages.withPackages (epkgs: [ epkgs.maak ])
#+end_src

** Which one?
:PROPERTIES:
:CUSTOM_ID: which-one
:END:

- *Guix* if you want the toolchain the project is tested with, and the ability to
  roll back a bad upgrade.
- *Nix* if the rest of your machine is already declarative; the flake pins
  nixpkgs and gives you a binary cache.
- *Container* if you only want to try the release, or reproduce a report on a
  machine that has nothing installed.
- *Distribution package* if you want the project managed by the same tool as the
  rest of your system, with its licence, manual page and launcher in the usual
  places.
